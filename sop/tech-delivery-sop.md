# 技术交付 SOP · T0 → T7

> **项目无关 · AI-Native by Design · 一份事实源**
>
> 本 SOP 描述一次研发交付从「PRD 已签」到「复盘归档」的 8 步主流程 + 1 个横切仪式。
> 主流程对**人**与 **AI agent** 一视同仁——执行者可换，工件 / Gate / 输入输出格式不变。
> AI 替换草稿生产环节的战术建议见 [ai-agent-playbook.md](../ai-agent-playbook.md)；本 SOP 不内嵌 AI 用法。

## 1 · 目的与定位

- **回答的问题**：一次研发交付要走哪些步骤 / 谁做 / 产出什么 / 怎么把关 / 谁拍板
- **覆盖范围**：T0 PRD Intake → T7 复盘归档
- **入口前置**：PRD 与原型已通过产品评审（产品评审不在本 SOP 范围）
- **与 playbook 的关系**：本 SOP = WHAT；[playbook](../ai-agent-playbook.md) = HOW（每步用什么 AI 招式）

### 1.1 拆分原则（为什么是 8 步 + R 横切）

每个步骤独立成立的判据：**Owner / 主产出 / Exit / 失败模式**四个维度任一不同即拆分。
ADR/STD 增量在任意步骤都可能被触发，不属于流水线某一站，所以单列为横切仪式 R，不占主序号。

### 1.2 适用范围

本 SOP 适用于**任何"PRD 已签 → 上线复盘"的研发交付**，与项目 / 语言 / 部署形态无关。具体适用形态：

- 新增服务 / 新增模块 / 新增 API 端点
- 现有功能的修改 / 重构
- 跨服务的协同变更（每个被影响服务各跑一遍 SOP，T2 契约一次成型由主导方拉齐）

### 1.3 不在本 SOP 范围内

以下场景**不走**本 SOP（各有专属流程，可能将来另立 SOP）：

| 场景 | 原因 |
|---|---|
| 紧急生产故障修复（Incident Hotfix）| 走 Incident Response，事后补 T7 复盘 |
| 纯运维操作（密钥轮换 / 备份恢复）| 走 Ops Runbook，不入 T0 |
| 探索性 Spike / 原型验证 | 不产出生产代码；产出报告后再决定是否进 T0 |
| 产品 / 设计评审 | 在 T0 之前完成；本 SOP 把 PRD 已签视为前置条件 |
| 文档单独修订 | 走文档自治流程；如涉及契约/规范变更走 R 横切 |

## 3 · 跨步通用约定（先看完，否则单步描述读不懂）

本节定义"在所有步骤里都成立"的横向规则。后面 T0–T7 各节会直接引用这些定义而不重复。

### 3.1 任务包（Task Package）

**定义**：T3 拆出来、T4 落地的最小工作单元。一个任务包应当**一个 PR 能关掉**（不行就再拆）。

**必含字段**（任务包模板）：

| 字段 | 说明 |
|---|---|
| `id` | 唯一编号（可由 Issue tracker 自动生成）|
| `title` | 一句话陈述要做什么 |
| `context_links` | 指回 PRD / 影响地图 / 契约文件的链接（让接手方零成本回溯）|
| `inputs` | 开始前必须就位的工件清单（契约 / 数据 / 上游服务）|
| `outputs` | 完成后产出的工件清单（代码路径 / 测试 / 文档段落）|
| `dor` | Definition of Ready（见下）|
| `dod` | Definition of Done（见下）|
| `estimate` | 估时（人时 / story point，单位由各团队 Layer 3 自选）|
| `owner` | 唯一负责人（不允许多人共担）|
| `dependencies` | 依赖的其他任务包 id |
| `status` | 引用 §3.2 Issue 状态机 |

**Definition of Ready（DoR · 才能进入 T4 实施）**：
- 所有 `inputs` 已存在且 Approved
- 任务包**钉死契约版本号**（不是「最新版」；任何上游契约升级是该任务包的显式变更）
- 验收标准在 `dod` 中可枚举
- 估时已完成且 Owner 已认领

**Definition of Done（DoD · 才能进入 T4.5 业务验收）**：
- 代码已合并主干
- 自动化测试覆盖关键路径并通过
- 相关文档段落（API / 操作手册 / Runbook）已更新
- T4.3 代码评审完成（5 红旗 checklist 全过）
- T4.4 QA 验收完成（无阻塞缺陷）

**需求规格（feature spec）与任务包（1:N · 共享规格）**

T2 详设以 **feature（需求）** 为单位产出一份**需求规格（feature spec）**；T3 在该规格内拆出 **N 个任务包（task package）**、每个任务包镜像为一个 Issue Tracker 跟踪条目（1 任务包 = 1 Issue = 1 PR）。

| 层级 | 载体 | 必含内容 | 数量关系 |
|---|---|---|---|
| **需求规格（feature 级 · 共享）** | git 入库的规格包（目录 / 多文件）| 需求陈述（WHAT/WHY）· 高层方案（HOW）· 接口 / 事件契约 · 数据模型 · 技术派生决策 · 验收场景 | **1 个 / feature** |
| **任务包（task 级 · 独立）** | 规格包内的任务清单一项 + Issue Tracker 一个条目 | 本节上方 11 字段（id / title / inputs / outputs / DoR / DoD ...） + 一条可机器执行的 `verification` | **N 个 / feature** |
| **跟踪条目（人看）** | GitHub / Linear / Jira Issue | 镜像任务包字段，扯通状态机 / 通知 / PR 闭环 | **1 : 1 / 任务包** |

**单一事实源分层（不可双写）**：
- **feature 级共享内容**（接口 / 数据模型 / 高层方案 / 验收场景）→ 事实源 = **规格包**（git diff / 回滚 / 分支并行）
- **task 级实施细节**（任务实现路径 / verification / 责任人 / 状态）→ 事实源 = **Issue 条目** + 规格包内的任务清单行（sync hook 负责双向一致）

**跟踪与闭环**：PR commit message 必带 `Closes #N` 闭单 task Issue；任一跨工件引用（PRD / 契约 / 任务包）必带**版本号**（§3.1 DoR 该段）。

**变更红线**：T4 任务包发现 feature 级规格缺漏 / 契约不可行 → **回流 T2** 修订规格并重走 Gate，**禁止在单 task 内私改** feature 级内容（避免同 feature 下 N task 发生契约偏移 / 棘轮魔改）。

**SOP 不锁定具体实现**：规格包的目录布局 / 子文件名 / 人机镜像工具 全属 HOW 层选型，由各项目 Layer 3 决定。本仓 AI 实施的具体目录契约与镜像命令（例如 Spec-Kit 的 `specs/NNN-<slug>/` 与 `/speckit.taskstoissues`）见 [ai-agent-playbook](../ai-agent-playbook.md) §1.5、§1.6、§7。

### 3.2 工件状态机

本 SOP 涉及 8 类工件。所有跨人协作以**状态变更**为事实，不以口头共识为事实。

| 工件 | 状态转移 |
|---|---|
| **PRD** | `Draft → Reviewed → Signed`（Signed 是本 SOP 入口）|
| **影响地图** | `Draft → Reviewed → Approved` |
| **契约**（OpenAPI / Schema）| `Draft → Lint Pass → Approved → Published(vN)`；**多版本可共存**，`Published(vN)` 与 `Draft(vN+1)` 并行存在 |
| **任务包 / Issue** | `Backlog → Ready(DoR met) → In Progress → In Review → Done(DoD met)` |
| **PR** | `Open → CI Pass → Reviewed → Merged`（或 `Closed without Merge`）|
| **发布单** | `Planned → Deploying → Deployed → Verified` 或 `Rolled Back` |
| **观测窗报告** | `Open → Window Closed → Report Filed`（含全部告警 ack/fix/误报标记）|
| **复盘文档** | `Draft → Discussed → Filed(with Action Items)`（每条 Action 有 Owner + 截止日才算 Filed）|

**幂等约束**：所有状态变更动作必须可重放（同样的输入触发多次，最终状态一致）——这是 P5 的实现保障。

**契约版本管理三条结果约束**（具体实现机制属 STD-API 层，本 SOP 不展开）：
- 所有契约文件必带 semver；任务包引用契约必带版本号
- 任何变更必有 changelog；breaking 变更必显式标注
- **Minor / Patch 变更**可由服务 Owner 在 T4 内自行发版，广播消费方；**Breaking 变更**必须回 T2 走完整 Approve

### 3.3 审批通用约束（适用所有工件）

本 SOP **所有有审批属性的工件**（影响地图 / 契约 / 任务包 / PR / 发布单 / 复盘 / ADR / STD）都遵循同一规则：每个工件有**指定审批角色**（见 §3.5 矩阵 · 可一个或多个，多个时全签生效），签字时必留**结构化检查记录**。

**结构化检查记录**（反惰性 · 唯一硬约束）：

- 红旗 checklist 逐项打勾 + 异常项备注
- 时戳 + 审批人身份
- 记录入工件历史，T7 复盘可审计
- **不要求强行产生改动**；要求「我看了什么、判断依据是什么」可追溯
- 长期监控：审批人总是秒过 + 零备注 → T7 暴露为指标（不实时拦截）

> **草稿来源不在本 SOP 约束范围**：工件草稿由谁产出（审批人自己 / 同岗他人 / AI 工具）属于实施层选择，本 SOP 不规定。AI 替换草稿生产环节的战术建议见 [ai-agent-playbook](../ai-agent-playbook.md)，C1 契约保证删掉 playbook 后本 SOP 仍可执行。

### 3.4 Gate（每步骤出口）

**Gate** = 步骤出口判据。所有步骤同构：T0–T7 每步 1 道 Gate，T4 展开的 T4.1–T4.5 同样每步各 1 道。

**Gate 判据形式只允许三种**：

| 判据形式 | 适用 | 示例 |
|---|---|---|
| **CI 信号** | 可自动化的客观判据 | lint / test / build / 安全扫描 |
| **红旗 checklist** | 经验类判据，能枚举为 N 条"是否中" | Code Review 红旗清单 / Audit checklist |
| **人 Approve** | 不可枚举的判断 / 不可逆操作前的最终背书 | 影响地图 Approve / 部署 Sign-off / 业务验收 |

> 任何 Gate 必须挑且只挑上面一种形式。“评审会大家觉得 OK 就过”不是合法判据。

**不可逆 Gate**（失败成本 ≥ 回滚成本）**必须**包含人 Approve：T2 契约 Published / T5 部署 / T7 复盘归档。

**所有 Gate 必须配 §3.3 结构化检查记录**（无记录的 Approve 在 T7 复盘视为缺陷）。

**Gate 失败回流矩阵**：

| Gate 失败 | 回到哪一步 |
|---|---|
| T0 自检不过 | 打回上游修 PRD |
| T1 评审不过 | 回 T1 重做影响地图 |
| T2 Lint 或评审不过 | 回 T2 改契约 |
| T3 Approve 不过 | 回 T3 重拆 |
| T4 出口不过（T4.1–T4.5 未全完成）| 按下方 T4 内部回流处理 |
| T5 健康检查不过 | **回滚** + 视情况回到 T4 修复 |
| T6 稳定阈值未达 | **Hotfix**（小问题）或回到 T4（大问题）|
| T7 复盘缺席 | 不阻塞下次交付，但记为技术债 |

**T4 内部回流**（T4 由 T4.1–T4.5 五步串行）：

| 步骤 Gate 未达 | 处理 |
|---|---|
| T4.1 方案未过 TL 5 条 checklist | 回 T4.1 改方案 |
| T4.2 CI 未全绿 | 留在 T4.2 继续改代码直到全绿 |
| T4.3 代码评审 5 红旗未全过 | 回 T4.2 修缺陷，重跑 T4.2 → T4.3 |
| T4.4 QA 有阻塞缺陷 | 回 T4.2 修缺陷，重跑 T4.2 → T4.4 |
| T4.5 业务验收任一项未 pass | 回 T4.2 修缺陷，重跑 T4.2 → T4.5 |

### 3.5 评审权限矩阵

**角色定义**（项目无关骨架；本 SOP 只定义**职责位**，谁担任 / 一人兼几岗 / 一岗几人由 Layer 3 各仓 AGENTS.md 决定）：

- `PO` · 产品负责人（业务侧），T0/T4.5 业务侧 Owner
- `TL` · Tech Lead，T0/T4.5 技术侧联签 Owner、T3 任务包拆分 Owner、跨服务协调
- `架构师` · T1/T2 主导 Owner
- `服务 Owner` · 单个服务的负责人，T2/T4 主要执行者
- `Dev` · T4 实施执行者
- `QA` · T4.4 QA 验收判定方
- `Release Owner` · T5 部署 Owner
- `SRE` · T6 观测窗 Owner
- `Eng Lead` · T7 复盘 Owner
- `架构委员会 / 标准组` · R 横切 Approver

**审批人矩阵**（每步骤 Gate · 按下表列出的角色全部签字生效；多个角色时联签）：

| 步骤 | 判定方 |
|---|---|
| T0 自检通过 | PO + TL |
| T1 影响地图 Approved | 架构师 |
| T2 契约 Approved | 架构师 + 所有受影响服务 Owner（全签）|
| T3 任务包 Ready | TL |
| T4.1 方案完成 | TL（5 条 checklist 点头） |
| T4.2 编码完成 | CI（机器判定全绿）|
| T4.3 代码评审完成 | 任意 Dev（非 PR 作者，5 红旗 checklist 全过）|
| T4.4 QA 验收完成 | QA |
| T4.5 业务验收完成 | PO + TL |
| T4 出口 | 上述 T4.1–T4.5 全完成 + PR Merged + Issue Done |
| T5 部署 Sign-off | Release Owner |
| T7 复盘归档 | Eng Lead |
| R · ADR / STD | 架构委员会 / 标准组 |

**串行 / 并行规则**：
- T0 → T1 → T2 → T3 → T4 → T5 → T6 → T7 主线**严格串行**
- T4 内部 T4.1 → T4.2 → T4.3 → T4.4/T4.5 串行；T4.4 与 T4.5 可并行
- R 横切可与任何步骤**并行**，但**步骤触发了 R 且依赖 R 产出时**该步骤必须暂停到 R Approved（见 §3.6）

### 3.6 R 横切触发规则

**何时必须开 ADR**：满足下列任一即必须开
- 不可逆决策（选型一旦落地难以回退：数据库 / 主语言 / 通信范式）
- 多候选选型且任一候选有显著权衡（性能 / 成本 / 复杂度）
- 跨 BC / 跨服务影响（影响 ≥ 2 个服务 Owner 的判断）

**何时必须改 STD**：满足下列任一即必须改
- 同一模式被复用 ≥ 3 次（应该提炼成标准）
- 触发横切红线（安全 / 合规 / 性能基线）
- 跨 ADR 之上出现共性（多个 ADR 都在解决同一类问题）

**触发后步骤行为**：

| 步骤 vs R 的关系 | 规则 |
|---|---|
| **阻塞型**：步骤要消费 R 的产出 | 该步骤暂停到 R Approved（典型：T2 契约依赖 R 选型；T4 实施依赖 R 标准）|
| **并行型**：R 与当前步骤无依赖 | R 在后台推进，步骤不暂停 |
| **追认型**：实施中发现已落地的做法需要事后记录 | 不阻塞实施，但必须在 T7 复盘前补 R |

**ADR 与 STD 的边界**：

| 类型 | 回答 | 触发频率 |
|---|---|---|
| **ADR** | "在 N 个候选里**为什么**选 X" | 每次决策一篇 |
| **STD** | "所有人**必须怎么写**" | 沉淀为可复用规范 |

## 4 · T0 · 需求 Intake

| 维度 | 内容 |
|---|---|
| **Owner** | PO + TL |
| **输入** | Signed PRD + 原型 |
| **主产出** | T0 自检清单（结构化检查记录，按 §3.3）|
| **Exit Criteria** | 8 项自检全部通过 |
| **失败模式** | 任一项不通过 → 打回 PRD 上游修复，本步停止 |
| **判定方** | PO + TL |

### 4.1 自检清单（8 项 · 红旗 checklist）

| # | 项 | 通过判据 |
|---|---|---|
| 1 | 业务目标明确 | 一句话陈述「为谁解决什么问题」|
| 2 | 验收标准可测 | 全部以「输入 → 期望输出」可枚举 |
| 3 | 关键路径有原型 | 每条主路径至少 1 张原型或线框 |
| 4 | 外部依赖识别 | 列出第三方 / 上游服务 / 数据源 |
| 5 | 合规 / 安全约束识别 | 涉及个人信息 / 资金 / 监管的标红 |
| 6 | 数据范围识别 | 新增 / 修改的数据实体、数据量级 |
| 7 | 失败 / 异常分支定义 | 主路径外至少 1 条失败路径 |
| 8 | 估算量级 | 给出 S / M / L 量级（不要求精确） |

## 5 · T1 · 影响分析

| 维度 | 内容 |
|---|---|
| **Owner** | 架构师 |
| **前置条件** | **架构基线就绪**（BC 划分 / 服务清单 / 总线契约 已存在且被认为有效）。若无基线或本次 SPEC 完全破坏基线 → 不走 T1，先回 **R · ADR-架构基线**（见 §3.6）立 / 更新基线，再进 T1 |
| **输入** | T0 通过的 PRD + 自检清单 + 架构基线快照 |
| **主产出** | 影响地图（结构化矩阵 · vs 基线 delta）|
| **Exit Criteria** | 架构师 Approve + 所有受影响服务 Owner ack |
| **失败模式** | 地图不全或评审不过 → 重做；基线不存在被误走 T1 → 退回 R |
| **判定方** | 架构师 |

### 5.1 影响地图必含维度

| 维度 | 说明 |
|---|---|
| **限界上下文（BC）** | 落在哪一 / 哪几个 BC |
| **服务 / 模块** | 影响哪些服务及其负责人 |
| **API 端点** | 新增 / 修改 / 弃用 的端点清单 |
| **事件 / Schema** | 新增 / 修改 的事件主题与 Schema |
| **数据实体** | 影响的数据表 / 文档结构 / 迁移需求 |
| **角色 / 权限** | 触及的角色与权限变化 |
| **横切标准（STD）** | 触发哪些标准的引用或修订 |
| **跨 BC 协作模式** | 同步调用 / 事件驱动 / Saga 等 |

### 5.2 R 触发判定

影响地图完成后**必须**主动判定是否触发 R（按 §3.6 ADR / STD 触发条件）。触发即开 ADR / STD，按阻塞型暂停 T2。

## 6 · T2 · 详设 + 契约先行

| 维度 | 内容 |
|---|---|
| **Owner** | 架构师 + 所有受影响服务 Owner |
| **输入** | Approved 影响地图 + R（如有）产出 |
| **主产出** | 需求规格（feature spec：含 OpenAPI / 事件 Schema / 数据模型 / 验收场景）+ services/&lt;svc&gt;.md 增量 |
| **Exit Criteria** | 契约 Lint Pass + 全签 Approve + `Published(vN)` |
| **失败模式** | Lint / 评审不过 → 改契约重跑；若涉及选型分歧 → 触发 R · ADR |
| **判定方** | 架构师 + 所有受影响服务 Owner（全签） |

### 6.1 契约 Lint 必检项

- OpenAPI / Schema 语法 lint 通过
- 命名规范符合 STD-API（端点 / 字段 / 错误码）
- 安全敏感字段（个人信息 / 资金 / 凭据）显式标注
- 事件 Schema 与对应 API 字段类型一致
- 必带 semver 与 changelog（§3.2 三条结果约束）

### 6.2 契约先行的硬约束

T3 不允许在「契约 Published 之前」拆任务包；任务包必引用具体版本号（§3.1 DoR）。Minor / Patch 升级允许并行（§3.2），Breaking 必须回 T2 全签。

## 8 · T4 · 实施（T4.1–T4.5 串行）

| 维度 | 内容 |
|---|---|
| **Owner** | Dev（每任务包唯一 Owner，按 §3.1）|
| **输入** | `Ready` 状态的任务包 |
| **主产出** | 代码 + 测试 + PR + 更新后文档段落 |
| **Exit Criteria（T4 出口 Gate）** | T4.1–T4.5 全完成 + PR `Merged` + Issue `Done`（DoD met）|
| **失败模式** | 任一步骤 Gate 未达 → 按 §3.4「T4 内部回流」处理 |
| **判定方** | 无单一审批人 · T4.1–T4.5 各自判定方聚合（见 §8.1–8.5）|

> 每个任务包独立跑一遍，分 5 步执行：T4.1 → T4.2 → T4.3 → T4.4（T4.5 可与 T4.4 并行）。

### 8.1 T4.1 · 写方案

| 维度 | 内容 |
|---|---|
| **Owner** | Dev（任务包负责人）|
| **输入** | `Ready` 状态的任务包 + Published 契约 |
| **主产出** | 1 页方案文档 + Tech Lead 结构化检查记录 |
| **Exit Criteria** | Tech Lead 按 5 条 checklist 全部打勾：① 拆解合理 ② 测试方案覆盖关键路径 ③ 回滚方案明确 ④ 风险登记 ⑤ 涉及契约变更 → 已走 §3.2 流程 |
| **失败模式** | 任一项未勾 → 回 T4.1 改方案（§3.4） |
| **判定方** | Tech Lead |


### 8.2 T4.2 · 编码

| 维度 | 内容 |
|---|---|
| **Owner** | Dev（任务包负责人）|
| **输入** | T4.1 通过的方案文档 |
| **主产出** | 代码 + 测试 + PR + CI 报告（自动归档）|
| **Exit Criteria** | CI 全绿：lint / unit test / integration test / build / 安全扫描 / 契约一致性测试 |
| **失败模式** | CI 未全绿 → 留 T4.2 继续改直到全绿（§3.4） |
| **判定方** | CI（机器判定，无人审批）|


### 8.3 T4.3 · 代码评审

| 维度 | 内容 |
|---|---|
| **Owner** | 任意 Dev（非 PR 作者）|
| **输入** | T4.2 通过 CI 的 PR |
| **主产出** | PR Review 记录（5 红旗 checklist 打勾 + 备注）|
| **Exit Criteria** | 5 条红旗 checklist 全过：① 复杂度可控 ② 契约一致 ③ 错误处理完整 ④ 可观测点充足 ⑤ 安全 / 合规无红旗 |
| **失败模式** | 任一红旗未过 → 回 T4.2 修缺陷重跑 T4.2→T4.3（§3.4） |
| **判定方** | 任意 Dev（非 PR 作者）|


### 8.4 T4.4 · QA 验收

| 维度 | 内容 |
|---|---|
| **Owner** | QA |
| **输入** | T4.3 通过评审的 PR + 测试用例 + 性能基线 |
| **主产出** | QA 测试报告 + 缺陷登记 |
| **Exit Criteria** | 测试用例全过 / 探索性测试无阻塞缺陷 / 性能基线达成 |
| **失败模式** | 有阻塞缺陷或性能未达 → 回 T4.2 修缺陷重跑 T4.2→T4.4（§3.4） |
| **判定方** | QA |


### 8.5 T4.5 · 业务验收

| 维度 | 内容 |
|---|---|
| **Owner** | PO + TL |
| **输入** | T4.3 通过评审的 PR + PRD 验收标准（可与 T4.4 并行）|
| **主产出** | 验收记录（PRD 验收标准逐条对照表）|
| **Exit Criteria** | DoD 全部满足 + PRD 验收标准逐条 pass |
| **失败模式** | 任一项未 pass → 回 T4.2 修缺陷重跑 T4.2→T4.5（§3.4） |
| **判定方** | PO + TL |

## 9 · T5 · 部署

| 维度 | 内容 |
|---|---|
| **Owner** | Release Owner |
| **输入** | 所有任务包 T4.5 业务验收完成 + PR Merged |
| **主产出** | 发布单（`Planned → Deploying → Deployed → Verified` 或 `Rolled Back`）|
| **权限红线** | 部署执行权只属于 Pipeline（自动化）或人（SRE / Release Owner）。**AI 无 prod 环境写权限**（集群 / DB / DNS / Secret）；AI 只能产出草稿、观察指标、输出“回滚 / 扩量 / 继续”建议，不可被授予触发部署或回滚的控制面凭证 |
| **Exit Criteria** | Deploy 成功 + 健康检查通过 + Release Owner Sign-off（不可逆 Gate · 必须人 Approve）|
| **失败模式** | 健康检查不过 → **回滚**（人触发预定义剧本）；视情况回到 T4 修复 |
| **判定方** | Release Owner |

### 9.1 部署单必含

- 变更范围（任务包列表 / PR 列表 / 契约版本）
- 部署策略（蓝绿 / 金丝雀 / 滚动）
- 健康检查项与判据
- 回滚剧本（明确的命令 / 步骤）
- 通知清单（受影响方）

## 10 · T6 · 观测窗

| 维度 | 内容 |
|---|---|
| **Owner** | SRE + Dev |
| **输入** | 已部署且 `Verified` |
| **主产出** | 观测窗报告 |
| **Exit Criteria** | 观测窗内稳定阈值达成 + 全部告警有 ack/fix/误报 标记 |
| **失败模式** | 阈值未达 → **Hotfix**（小问题）或回 T4（大问题）|
| **判定方** | SRE |

### 10.1 观测窗时长建议

| 变更等级 | 建议时长 |
|---|---|
| 小变更（少量字段 / 配置）| 24h |
| 中变更（新端点 / 新事件）| 72h |
| 大变更（新服务 / 跨 BC 协作变更）| 1 week |

> 具体阈值与判定由 Layer 3 各仓 AGENTS.md 按业务特性定。

### 10.2 报告必含

- 观测窗起止时间
- 告警列表 + 每条的 ack / fix / 误报 标记
- 关键指标对比（部署前 vs 部署后）
- 是否触发 Hotfix；触发则附 Hotfix 单

| **判定方** | Eng Lead |

### 11.1 Audit Checklist（示例 · 随实践迭代）

> 人复盘与 AI 自审用同一份清单。下表为初版条目，随 T7 复盘累计补充与精炼。

| # | 项 | 关注 |

| 6 | **审批人留痕质量** | 结构化检查记录是否完整、是否有秒过 |
| 7 | **R 横切合理性** | 追认型 R 是否过多（应前置） |
| 8 | **告警 / 事件分析** | 观测窗告警与预期是否一致 |
| 9 | **上轮 Action 闭环率** | 上次复盘 Action 完成情况 |

### 11.2 Action Items 必含字段

- 描述 / Owner / 截止日 / 关联项目（R / SOP 自身 / playbook）

## 12 · R · ADR / STD 增量（横切仪式）

| 维度 | 内容 |
|---|---|
| **Owner** | 提出方（任意角色都可发起）+ 架构委员会 / 标准组 |
| **触发条件** | §3.6 触发规则（不可逆决策 / 多候选 / 跨 BC；或同模式 ≥ 3 次复用 / 横切红线 / 跨 ADR 共性）|
| **主产出** | ADR.md 一篇 / STD-NN/*.md 一节 |
| **Exit Criteria** | 架构委员会 / 标准组 Approve（不可逆 Gate · 必须人 Approve）|
| **失败模式** | 改提议重提；不阻塞已并行推进的步骤（除非阻塞型，按 §3.6）|
| **判定方** | 架构委员会 / 标准组 |

### 12.1 ADR / STD 模板（项目无关骨架）

| 类型 | 必含段落 |
|---|---|
| **ADR** | 背景 / 决策 / 候选方案对比 / 权衡 / 结论 / 变更记录 |
| **STD** | 适用范围 / 规则条目（编号）/ 反例 / 检查方法 / 变更记录 |

> 具体格式由 [tech-standards/STD-00-meta](../../tech-standards/) 或对应仓的标准目录定义。

## 13 · AI-Native 8 范式自检（C5 的可检查形式）

| # | 范式 | 在本 SOP 哪一步体现 |
|---|---|---|
| **P1** | 工件驱动（不是会议驱动）| §2 每步都有"主产出" |

| **P6** | 上下文有边界单元 | §3.1 任务包 |
